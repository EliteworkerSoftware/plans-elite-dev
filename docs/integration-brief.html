01

Why this document exists

Your dev is walking into this cold. This is everything he'd otherwise have to reverse-engineer from a 14,800-line codebase before he could give you an honest estimate.

The plan-markup tool has been running as its own small product for a while — its own login, its own database, its own hosting. The plan now is to fold it into eliteworker, sitting inside a customer's job page instead of living on its own. This brief covers the current architecture end to end, the decisions already made about what carries over, and the questions that are still open — so the estimate he gives you is grounded in what's actually there, not a guess.

02

What it is today

A hand-built, five-page static site — no framework, no build step, no bundler.

Every page is plain HTML with inline (now partly extracted) CSS and JavaScript, deployed by uploading files straight to Apache/IONOS hosting at plans.elitesmarthome.com. There's no package.json, no compile step — a browser loads the files exactly as written. The backend is entirely Supabase: Postgres, file storage, realtime, and two serverless functions.

03

The Supabase backend

Not just a database — four separate services, each with its own migration story.

Database — customer & job hierarchy

The tool keeps its own parallel copy of customers and jobs: a customer has locations (addresses), a location has projects (the actual markup jobs), a project has variants (revisions).

TableHoldsFate in target
markup_customersName, type, archived flagdrop — eliteworker owns customers
markup_locationsAddress, linked to a customerdrop — eliteworker owns addresses
markup_projectsThe job/plan itself — annotations, PDF path, an unused eliteworker_job_id columnkeep, reshaped — becomes the join point
markup_variantsNamed revisions of a project (e.g. multiple PDF tabs)keep
The seam to build on

markup_projects.eliteworker_job_id already exists in production — a text column, sitting empty, referenced nowhere in the code. Someone planned for exactly this integration and never finished wiring it up. It becomes the one foreign key a project needs once customers/locations move to eliteworker.

Database — identity & access

Database — AI placement cluster

Confirmed with the owner: the auto room-detection / auto icon-placement feature doesn't work and isn't used. Its tables come out entirely rather than migrating — see AI Features below for the full breakdown of what stays and what goes.

Storage

Every plan PDF lives in a Supabase Storage bucket named plan-pdfs — uploaded, downloaded, listed, and deleted from roughly two dozen call sites across app.js. Whatever eliteworker already uses for file storage (S3, local disk) is a direct replacement; this isn't a small feature to skip.

Realtime

One presence channel per open project (presence:<projectId>) shows which teammates currently have a plan open. It's a single, self-contained feature — not deeply wired into the rest of the app — which makes it cheap to either rebuild with Laravel broadcasting or drop.

Edge Functions

Source not in this repo

Mail-Send (invite/reset emails) and user-mgmt (admin add/deactivate/delete-user actions) run as Supabase Edge Functions. Their code only exists inside production's Supabase dashboard — it needs to be pulled out before your dev can port the logic into Laravel controllers.

Cutting the placement cluster also removes the need to migrate floor_plan_annotations, floor_plan_labels, and ai_placement_history — three fewer tables in the target schema.

Security note — applies regardless of which features stay

Every Claude call today runs client-side, using an API key pulled from localStorage (and a shared fallback in app_config) — visible in plain text to anyone who opens devtools. When Smart Merge (and image search, if it stays) moves into Laravel, the call needs to go through a server endpoint that holds the key — this is a real fix to scope, not optional cleanup.

05

Technical debt worth knowing about

Small discrepancies found while pulling the real schema — none are blockers, but your dev should know they exist before he's confused by them mid-build.

  • supabase-setup.sql in the repo only defines 2 of the 13 real tables — it's stale and not something to build from, only kept here as a historical artifact.
  • Two tables the client code queries — floor_plan_room_boxes and placement_examples — don't exist in the current production schema. Both belong to the AI placement cluster being cut anyway, so this is moot rather than a bug to chase.
  • markup_users.anthropic_key is written to and read by the code, but no such column exists in production — that write has likely been silently failing. Also moot once the cluster using it (placement/chat) is cut.
  • markup_projects.client is a legacy free-text field that predates the proper customer_id/location_id relationship — drop it in the target schema.

Already prepped

A safe, fully isolated place for your dev to explore the running app without any risk to production.

  • Production — plans.elitesmarthome.com on IONOS — untouched by any of this work.
  • Repo — github.com/EliteworkerSoftware/plans-elite-dev, public, auto-deploys on push.
  • Live duplicate — plans-elite-dev.vercel.app, updates within a minute of any push to the repo.
  • Isolated Supabase project — separate URL and keys from production; safe to test sign-in, the markup canvas, and admin actions against without touching real customer data.
  • app.html already decomposed into app.html / app.css / app.js, verified working end to end.

Not yet done: admin.html, index.html, invite.html, and forgot.html are still monolithic single files, and no audit has been done yet for hardcoded root-relative paths that would break if the tool ends up living at a subpath inside eliteworker instead of a domain root.

07

What ships vs. what's chrome

Owner's call: strip the standalone-app shell, keep the editing engine untouched.

Today's app.html menu bar is built like a desktop application — a logo that links to a project dashboard, File / Edit / View dropdown menus, a save-status indicator, a theme toggle, and an account badge. Inside eliteworker, that entire top bar is redundant: eliteworker's own shell already provides navigation, theming, and account context. None of it should be rebuilt inside the embedded tool.

The "dashboard" that File → Open Project currently leads to isn't a separate page — it's an internal view inside app.html that lists every markup project across every customer (loadJobDashboard()). That browsing view goes away entirely: when eliteworker launches the tool from a specific job, it's already scoped to that one job — there's nothing to browse.

Commands living in the File/Edit/View dropdowns today — Undo/Redo, zoom, Export to PDF, Save As, Storage Manager — still need a home in the embedded UI. Removing the desktop-style menu bar doesn't mean removing what it does; it means those actions move into the canvas toolbar itself (several already live there) or into whatever chrome eliteworker provides around the embedded panel.

09

Scoping checklist

What your dev needs answered before "how long will this take" has a real number behind it.

1

File storage backend

Does eliteworker already store files on S3 (or similar), or local disk? Plan PDFs can be large — this decision shapes the storage migration, not just a config swap.

2

Realtime presence — rebuild or drop

The "who's viewing this plan" indicator is the one piece without an obvious 1:1 Laravel equivalent. Worth the broadcasting setup, or cut?

3

Icon image search — keep or cut

Not addressed by either AI decision made so far. A small, separable feature — confirm before it's scoped in or out.

4

Who owns the Anthropic key going forward

Smart Merge (and image search, if kept) needs its API call proxied through a Laravel endpoint instead of running from the browser. Someone needs to own that key and its billing.

5

Does eliteworker's user model have roles already

The tool distinguishes admin vs. tech. Confirm whether eliteworker's existing permission system already covers this or needs extending.

6

Edge function source

Mail-Send and user-mgmt need to be pulled from production's Supabase dashboard before their logic can be ported — they don't exist anywhere in this repo.

7

Target timeline

Backlog item, or does this have a date attached? Changes whether a full rewrite or an incremental approach makes more sense.

8

Where do Undo/Redo, zoom, and Export to PDF live

Stripping the File/Edit/View menu bar (see What ships vs. what's chrome) still leaves those commands needing a home — in eliteworker's own panel chrome, or rebuilt into the canvas toolbar.
